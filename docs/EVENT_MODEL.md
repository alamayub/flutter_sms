# Event Model & Referential Integrity (Phase 4)

## Overview

The synchronization mechanism is entirely **event-driven**. Rather than sending raw table snapshots or arbitrary SQL statements, clients and the server exchange discrete, self-contained **Sync Events**.

Every write operation performed by a user generates a immutable event that is appended to the local queue, transmitted to the central server, assigned a global monotonic sequence number, and fanned out to peer devices.

---

## 1. Sync Event Anatomy

A sync event adheres to a strict canonical JSON schema:

```json
{
  "sequence": 142,
  "eventId": "a7b3c2e1-4567-4890-abcd-ef0123456789",
  "schoolId": "sch_rural_01",
  "deviceId": "c3e14674-8845-4228-a53b-e0fa95d6cbbf",
  "userId": "usr_admin_01",
  "entityType": "section",
  "entityId": "sec_5a_01",
  "operation": "create",
  "timestamp": "2026-09-10T09:00:00.000Z",
  "payload": {
    "id": "sec_5a_01",
    "schoolId": "sch_rural_01",
    "classId": "cls_grade5_01",
    "sectionName": "A",
    "roomNumber": "101",
    "capacity": 35
  }
}
```

### Attribute Definitions

- **`sequence` (int64)**: Monotonically increasing sequence assigned exclusively by the server in WAL mode. `null` while pending locally on a client.
- **`eventId` (UUID string)**: Globally unique identifier generated by the creating client. Guarantees **idempotency** — duplicate submissions of the same `eventId` are ignored.
- **`schoolId` (string)**: School database partition key.
- **`deviceId` (string)**: Hardware UUID of the originating device.
- **`userId` (string)**: ID of the authenticated user who initiated the action.
- **`entityType` (string)**: Canonical entity type (`school`, `academic_year`, `class`, `section`, `subject`, `teacher`, `student`, `enrollment`, `timetable`, `attendance`).
- **`entityId` (string)**: Primary key ID of the target record.
- **`operation` (string)**: Mutation type: `create`, `update`, or `delete`.
- **`timestamp` (ISO 8601 string)**: Timestamp of when the action occurred on the client device.
- **`payload` (JSON object)**: Full snapshot or modified fields of the entity.

## 2. Idempotency & Global Ordering

1. **Server-Side WAL Monotonic Sequencer**:
   Inside an immediate SQLite transaction:
   ```sql
   INSERT INTO sync_events (event_id, school_id, device_id, user_id, entity_type, entity_id, operation, payload, client_timestamp, server_timestamp)
   VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?);
   ```
   SQLite's auto-incrementing primary key provides a strictly ordered, gapless sequence number.
2. **Duplicate Ingestion Prevention**:
   The unique constraint `UNIQUE (school_id, event_id)` guarantees that if a network timeout occurs during push and the client retries, duplicate events are silently dropped without re-allocating sequence numbers.
3. **Deterministic Catch-Up**:
   Clients persist their last processed `sequence` in `sync_cursors`. Reconnection queries `GET /events?since={lastSequence}` guarantee zero skipped events and zero re-processed events.

---

## 3. Soft Deletes & Tombstones

To prevent catastrophic foreign key cascades and preserve historical records across disconnected devices:

- **No hard SQL `DELETE` is ever executed on synchronized core entities**.
- When a user deletes a record (e.g. archiving a Student or removing a Section), the operation is translated to a soft-delete tombstone:
  ```json
  {
    "operation": "delete",
    "payload": {
      "id": "stu_ada_01",
      "isArchived": true,
      "archivedAt": "2026-09-10T10:00:00.000Z"
    }
  }
  ```
- All entity handlers update the corresponding table: `isArchived = true`, `archivedAt = now()`.
- Filtered queries in the UI (`isActive = true AND isArchived = false`) exclude deleted items while retaining data integrity.

## 4. Referential Integrity & Deferred Events

In a distributed environment, network delays or batch chunking can cause a child entity to arrive at a peer device before its parent (e.g., an Attendance mark arriving before the Student record exists, or an Enrollment arriving before its Section).

Executing an immediate `INSERT` would trigger a foreign key constraint violation or leave orphan records.

### 4.1 Dependency Map

```
School (Root)
 ├── Academic Year
 │    ├── Class
 │    │    └── Section
 │    │         ├── Enrollment (links Student + Section)
 │    │         ├── Timetable (links Subject + Teacher + Section)
 │    │         └── Attendance (links Student + Section)
 │    └── Subject
 ├── Teacher
 └── Student
```

### 4.2 The `DeferredEventManager` Architecture

1. **Dependency Check**: When an `EntitySyncHandler` processes an incoming event, it checks if all foreign key parent entities exist in the local SQLite database.
2. **Persistent Deferral**: If a parent entity is missing:
   - The handler defers the event.
   - The event is serialized into the `sync_deferred_events` table with `missing_parent_id` and `missing_parent_type`.
   - The incoming sync loop continues without crashing or blocking other entities.
3. **Cascade Resolution**:
   - Whenever any parent entity is successfully inserted or updated:
   - The handler notifies `deferredEventManager.retryDeferredFor(entityType, entityId)`.
   - The deferred manager immediately retrieves all matching pending child events and reapplies them in correct topological order.
   - Resolved deferred events are removed from `sync_deferred_events`.
